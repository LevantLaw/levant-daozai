# 动画渲染与空闲功耗实践

- 日期：2026-11-19
- 适用范围：岛仔桌面端（Rust + egui，Windows 分层窗口，兼容渲染读回）
- 相关文档：PRD-001《AI 会话监控与岛上应答》
- 相关提交：`196d470`（AI 会话与事件驱动吉祥物）

## 结论先行

空闲不是一种需要持续表演的状态。吉祥物只在悬停、状态变化、事件反馈和音乐播放时动画；没有这些条件时，动画时钟冻结，画面停在当前姿势。配合分级重绘和兼容渲染读回限速，折叠态 60 秒空闲采样中，单核 CPU 从 12.47% 降到 6.82%，GPU 从 0.65% 降到 0.03%，内存保持稳定。

本文记录这次改动的判断依据、实现方式、测量方法和容易踩的坑，供后续动画和后台任务参考。

## 1. 问题：折叠态为什么反而更费电

岛仔是即时模式 UI：每一帧都重新描述界面，再由 Windows 分层窗口呈现。开启兼容渲染时，画面还要经过一次截图读回，才能交给分层窗口。

改动前的折叠态有三个持续开销：

1. 吉祥物一直在做空闲摆动、眨眼和睡眠呼吸，`repaint_after` 长期停在几十毫秒。
2. 只要吉祥物“可见”，界面就按动画帧率重绘，即使这一帧和上一帧几乎没有差别。
3. 兼容渲染的截图事件会再触发一帧；如果读回间隔比界面自己的节奏更密，就会形成“截图 → 重绘 → 再截图”的反馈环。

这解释了一个反直觉的现象：展开态看起来内容更多，但吉祥物被面板遮住，动画停止，CPU/GPU 反而更低；折叠态内容少，却因为吉祥物持续动画和读回而更费电。用户当时在任务管理器中观察到折叠态约 1.7% CPU、2% GPU，展开态约 0.5% CPU、0.2% GPU，方向与这个解释一致。

需要说明的是，任务管理器显示的是整机百分比；本文后面的探针数据是“单核百分比”和“系统百分比（单核 ÷ 逻辑处理器数）”。两者的分母不同，不能直接比较。

## 2. 设计原则

这次改动遵循六条原则：

1. **动画由事件驱动，不由帧循环驱动。** 状态变化、悬停、事件反馈、音乐播放才需要动画；空闲没有动画。
2. **时间源要可暂停。** 吉祥物使用独立时钟，只在动画期间前进；空闲时冻结，恢复时从原姿势继续，不跳相位。
3. **重绘频率按内容分级。** 形变 60fps，环境动画 30fps，吉祥物 10fps，等待态 120ms，空闲 1s；不要用一个全局帧率覆盖所有场景。
4. **不可见就不推进、不绘制。** 面板展开、极简模式、吉祥物关闭时，冻结状态和动画；恢复时用短暂过渡重新进入。
5. **读回跟随内容变化。** 兼容渲染只在画面变化或交互时连续读回；静止时按低频节奏走，不能形成 60fps 反馈环。
6. **定时器只做低频兜底。** 状态超时、清理、保留期用 1s 或更长；等待确认用 120ms；没有事件时不做高频轮询。

## 3. 吉祥物：独立时钟与事件窗口

### 3.1 两个时间

`App.t` 是界面时间，用于弹簧、过渡、通知等全局动效。吉祥物另有 `Pet.clock`，只在“应该动”的时候前进：

```rust
let moving = self.pet_a > 0.01
    && (self.pet.hovered
        || self.pet.reaction.is_some()
        || self.pet.waking_until > self.t
        || self.pet.expressions.current().is_some()
        || self.t < self.pet.anim_until
        || state == PetState::Music);
if moving {
    self.pet.clock += self.dt as f64;
}
let dt = if moving { self.dt } else { 0.0 };
let gaze = if moving { /* 跟随指针 */ } else { [0.0, 0.0] };
self.pet.advance(dt, visible);
self.pet.step(state, self.pet.clock, dt, gaze, visible);
```

`moving` 的六个条件分别对应六类合法动画：

- `hovered`：指针在吉祥物附近，眼神跟随指针。
- `reaction` / `expressions`：完成、失败、提醒等事件反馈。
- `waking_until`：从睡眠或发呆中唤醒的 2.2 秒过渡。
- `anim_until`：状态变化或淡入后的 1.2 秒过渡窗口。
- `Music`：音乐播放是持续状态，不是空闲。

`Pet::step` 内部还有一层可见性门控：`age` 只在 `visible` 时累加；反应剩余时间也只在可见时递减，避免用户还在面板里操作时，反馈已经播完。

### 3.2 为什么要冻结时钟

吉祥物的空闲摆动、眨眼和睡眠呼吸都直接使用传入的时间：

```rust
let mut y = (t as f32 * 1.7).sin() * 0.35;
// 眨眼窗口：每 5.6 秒一次
let start = 2.0 + hash01((t / 5.6).floor() as u64) * 2.7;
let blink = ((t % 5.6) as f32 - start) / 0.18;
```

如果界面不重绘、但时间仍用墙钟，屏幕看起来静止，下一次恢复时相位已经跳过了很多个周期，吉祥物会突然换一个姿势或直接眨眼。用可暂停的 `clock`，恢复时从离开时的相位继续，姿势连续。

冻结时钟也会带来一个新问题：如果冻结时眼神停在某个偏转角度，恢复后可能一直看着旧方向。解决办法是在恢复时给一个短暂的过渡窗口：

- 悬停进入或离开时，`anim_until = t + 0.4`，让眼神回到指针或中心，再静止。
- 淡入（`pet_a < 0.7`）或状态变化时，`anim_until = t + 1.2`，让眼睛、姿态和表情完成过渡。

### 3.3 不可见时的处理

面板展开、拖动热区、吉祥物关闭时，`update_pet` 在计算状态之前直接返回：

```rust
let available = allowed && !self.open && !self.drag_hot;
self.pet_a = anim::approach(self.pet_a, if available { 1.0 } else { 0.0 }, 9.0, self.dt);
if !available {
    return;
}
```

这样做有三个效果：

- 状态、表情、唤醒计时和动画时钟都不再推进。
- 吉祥物淡出，但不会在不可见时“偷偷”播放完反馈。
- 收起面板后，`pet_a < 0.7` 触发 1.2 秒过渡，从当前状态重新进入，而不是停在旧姿势。

### 3.4 音乐和睡眠

音乐是持续状态，`state == PetState::Music` 会让 `moving` 一直为真，但重绘仍按 10fps 走；眼睛形变的跟随速度降到 0.2 倍（`eye_dt = dt * 0.2`），避免低帧率下眼神抖动。

睡眠的 z 字浮动使用冻结后的时钟，发呆本身是静态姿势，因此空闲时完全静止。这是有意为之：如果希望“睡觉也有轻微呼吸”，应把呼吸改成独立、低频、可配置的动画，而不是让整个界面回到持续重绘。

## 4. 分级重绘

基础重绘间隔由 `App::frame` 根据当前场景决定；AI 的两行由 `agent_tick` 通过 `ctx.request_repaint_after` 额外请求，与基础节奏叠加：

| 场景 | 判定 | `repaint_after` | 说明 |
|---|---|---:|---|
| 形变、翻页、悬停意图、淡入淡出 | `transitioning` | 1/60 s | 交互手感优先 |
| 媒体播放、番茄钟、流体皮肤、会议提示 | `ambient` | 1/30 s | 30fps 足够 |
| 吉祥物悬停、事件、音乐 | `pet_moving` | 0.1 s | 稳态 10fps |
| AI 等待确认/回答 | `waiting > 0` | 120 ms | 状态灯和等待反馈 |
| AI 详情页，或 AI 页展开且有会话 | `detail` / `open` | 1 s | 计时和文本 |
| 空闲 | 以上都不满足 | 1 s | 时钟和状态兜底 |

优先级是 `transitioning > ambient > pet_moving > 空闲`。`animating` 等于前三者之一，测试用它判断“当前是否真的有动效”；兼容渲染读回则直接拿 `repaint_after` 做限速。

几个容易混淆的点：

- `pet_visible` 只表示吉祥物在画面上，`pet_moving` 才表示它需要动画。可见但静止时，不应该按动画帧率重绘。
- 过渡期间即使吉祥物在动，也可能由 `transitioning` 的 60fps 主导；10fps 是稳态值，不是所有时刻的硬上限。
- `request_repaint_after` 是提示，不是硬定时器；鼠标移动、点击、滚轮等输入仍会唤醒帧。不要依赖它做精确计时。
- 全局 10fps 看似简单，但会让静态内容也每秒重绘 10 次，并让形变过渡变粗糙；分级重绘比单一帧率更合适。

## 5. 兼容渲染读回

兼容渲染的关键约束是：截图事件本身会触发下一帧。如果读回间隔太短，界面会被读回“带着”跑到 60fps，哪怕内容没有变化。

`readback_delay` 做了两件事：

```rust
pub fn readback_delay(
    last: Option<Instant>,
    now: Instant,
    interactive: bool,
    pace: Duration,
) -> Option<Duration> {
    if interactive {
        return None;
    }
    let interval = AMBIENT_READBACK.max(pace);
    let elapsed = now.saturating_duration_since(last?);
    (elapsed < interval).then(|| interval - elapsed)
}
```

- `interactive` 为真时立即请求，保证拖动、点击、翻页跟手。
- 否则读回间隔取 `AMBIENT_READBACK`（33ms）和界面自身 `pace` 的较大值。界面只要求 10fps 时，读回不会按 60fps 跑；界面要求 60fps 时，读回最多 30fps，避免读回反过来把界面推到 60fps。
- `present_frame` 会比较这一帧和上一帧；画面没变且没有输入时，不再请求下一次截图。静止时因此不会连续读回。

项目代码里记录过一次相关排查（#170）：DX12 下闲置时读回反馈环曾让单核占用达到约 17%。这次的分级重绘和读回限速，是把同一个问题从“动画帧率”层面再收一遍。

页内翻页属于交互帧：`page_transition` 为真时读回立即请求，翻页结束后再回到 `pace`。隐藏或全屏裁掉画面时，呈现区域为零，不应再为不可见的动画请求高频读回；保留低频状态检查即可。

## 6. 定时器与后台状态

动画之外，后台任务也遵循同一套思路：**事件驱动为主，低频轮询兜底**。

- AI 会话：桥接是本地回环线程，Hook 事件到达时中继进程直接投递；`agent_tick` 在模块关闭时直接返回。等待确认/回答时 120ms 一次，其余情况 1s 一次，并且只有详情页、等待态或 AI 页有会话时才请求重绘。
- 天气、邮箱、日历、额度、剪贴板、喝水、久坐、专注、待办：由对应页面开关控制；关闭后不启动服务、不轮询、不提醒。
- 媒体：SMTC 轮询线程一直存在，但音乐页关闭时清空状态并 250ms park，不查询播放器。
- 更新检查：全局低频任务，不受页面开关控制；系统采样、托盘、输入等核心线程始终运行。

定时器本身也有两个建议：

1. **用绝对截止时间，不用累加计数。** `anim_until`、`waking_until`、会话保留期都用“到某个时刻为止”，避免 `dt` 累加漂移。
2. **清理和保留期不需要高帧率。** AI 会话默认保留 30 分钟、闲置 10 分钟标记过期，放在 1s tick 里检查即可；没有必要为了计时让界面每秒重绘几十次。

## 7. 测量方法与结果

### 7.1 方法

探针按进程采样，避免任务管理器口径带来的歧义：

- CPU：`Process.TotalProcessorTime` 的增量除以墙钟时间，得到“单核百分比”；再除以逻辑处理器数，得到“系统百分比”。
- GPU：`Win32_PerfFormattedData_GPUPerformanceCounters_GPUEngine` 中 `pid_<pid>_*` 的 `UtilizationPercentage` 求和。
- 内存：进程私有字节和工作集。
- 场景：折叠、无悬停、AI 页开启，启动后静置约 10 秒再采样 60 秒。

```powershell
$p = Get-Process daozai
$procId = $p.Id  # 多开时先确认要采样的 PID；$pid 是 PowerShell 自动变量，不能混用
$t0 = $p.TotalProcessorTime.TotalSeconds
$w0 = Get-Date
Start-Sleep -Seconds 60
$p.Refresh()
$t1 = $p.TotalProcessorTime.TotalSeconds
$w1 = Get-Date
$oneCore = ($t1 - $t0) / ($w1 - $w0).TotalSeconds * 100
$system = $oneCore / [Environment]::ProcessorCount

$gpu = Get-CimInstance Win32_PerfFormattedData_GPUPerformanceCounters_GPUEngine |
    Where-Object { $_.Name -like "pid_${procId}_*" } |
    Measure-Object -Property UtilizationPercentage -Sum
```

GPU 查询本身需要时间，60 秒窗口实际得到约 37 个有效样本；CPU 平均值仍按完整墙钟计算。

### 7.2 结果

同一台机器、同一套折叠设置、无悬停：

| 指标 | 改动前（吉祥物持续动画） | 改动后（空闲冻结） |
|---|---:|---:|
| 单核 CPU | 12.47% | **6.82%** |
| 系统 CPU（20 逻辑处理器） | 0.62% | **0.34%** |
| GPU 平均 | 0.65% | **0.03%** |
| GPU 峰值 | — | 1.0% |
| 私有内存 | — | 123.5 MB（60 秒内 123.5 → 123.8） |
| 工作集 | — | 130.8 MB |

单核 CPU 下降约 45%，GPU 下降约 95%。从代码路径和采样结果看，剩余的单核占用主要来自每秒一次的基础帧和兼容渲染读回，而不是吉祥物动画。GPU 平均接近零，说明静止时读回没有形成连续负载。

### 7.3 读数的边界

- 60 秒窗口不一定覆盖天气刷新、更新检查等分钟级任务；要更保守可以跑 5 分钟。
- GPU 利用率是各引擎的瞬时求和，峰值可能被单个短任务抬高；平均值和峰值要一起看。
- 进程私有内存不等于显存；任务管理器里的“显存”需要单独测。
- 任务管理器、探针、单核百分比、系统百分比的分母不同，不能跨口径直接比较。
- 测量时鼠标不要停在岛上，其他编译、测试、视频播放也会污染结果；建议重复 2–3 次取中位数。

## 8. 反模式

以下是需要避免的常见反模式，其中一部分在本次改动前确实存在：

1. **用全局 60fps 或全局 10fps 驱动所有内容。** 前者浪费，后者让形变和交互变粗糙；应按内容分级。
2. **“可见”就重绘。** 可见不等于在动；静止的吉祥物不需要动画帧率。
3. **用墙钟做可暂停动画。** 恢复时相位跳跃，姿势和眼神会突变。
4. **悬停离开没有缓冲。** 眼神会瞬间回中；0.4 秒的过渡更自然。
5. **读回间隔比界面节奏更短。** 截图事件会把界面推到更高帧率，形成反馈环。
6. **不可见时仍推进动画。** 反馈会在面板后面播完，用户看不到；应冻结并在恢复时过渡。
7. **用高频定时器发现低频事件。** 等待确认需要 120ms，清理和保留期 1s 就够；不要为了“实时”让空闲态持续轮询。
8. **每帧分配纹理或字体。** 长时间运行会增长内存；用数分钟的空闲测试观察内存曲线是否走平。
9. **测量时鼠标停在岛上。** 悬停会触发动画，测到的是交互态，不是空闲态。
10. **功能关闭后仍保留轮询和桥接。** 关闭页面就应停止服务、清空会话、移除桥接文件；Hook 可以保留，但中继应在没有桥接时立即返回。

## 9. 新动画检查清单

- [ ] 空闲时是否真的需要动？如果不需要，时钟是否冻结？
- [ ] 动画的最低可接受帧率是多少？10fps、30fps 还是 60fps？
- [ ] 元素不可见时，是否停止推进和绘制？
- [ ] 恢复时是否需要 0.4–1.2 秒的过渡，避免旧姿势或旧眼神？
- [ ] 是否用可暂停时钟，而不是墙钟？
- [ ] 重绘间隔是否和内容匹配，而不是全局固定值？
- [ ] 兼容渲染的读回是否被 `pace` 限速，交互帧是否有旁路？
- [ ] 功能关闭时，定时器、桥接、轮询是否全部停止？
- [ ] 长时间空闲后，内存和纹理是否稳定？
- [ ] 是否有“空闲不重绘、悬停才动画”的自动化测试？
- [ ] 是否在同条件、同场景下做过前后功耗对比？
